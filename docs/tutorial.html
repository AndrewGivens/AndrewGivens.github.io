Using Pull Requests When You Work Alone

A small, reproducible branch-to-merge workflow using a D&D challenge-rating plot.
Published

October 16, 2026

Why use a pull request when working alone?

Pull requests are often associated with team projects, but they can help when you work by yourself, too. A pull request gives you a review step before a change becomes part of your main branch. You can inspect exactly what changed, check the result, and keep a record of why you made the change. It is a little like setting your work aside, then returning to it with fresh eyes.

In this tutorial, we will make a small plot for a Dungeons & Dragons monster challenge-rating project. We will do the work on a branch, push that branch to GitHub, review it in a pull request, and merge it into main. The example data below is deliberately small and included in the script, so anyone can run the example without finding or downloading the same dataset. In a real analysis, you could replace the example rows with data from your own CSV.

Start with a separate branch

First, clone the project if you do not already have a local copy, then move into its folder. If you already have the project, start with the update and branch commands instead:

git clone https://github.com/AndrewGivens/dnd-challenge-rating-analysis.git
cd dnd-challenge-rating-analysis
git switch main
git pull origin main
git switch -c add-cr-plot

The first two commands download the repository and enter its directory. git switch main selects the main branch, and git pull brings it up to date with GitHub. The last command creates and switches to a new branch named add-cr-plot. A branch gives this one change its own workspace; the main branch stays as it was while we work.

Choose a name that describes the change. Names such as add-cr-plot or fix-missing-values make it easier to recognize what a branch is for later. GitHub’s guide to branches explains how branches fit into a typical workflow.

Make a small, checkable change

Create a file named plot_cr.py in the project folder. This example counts how many monsters appear at each challenge rating and saves a bar chart:

import pandas as pd
import matplotlib.pyplot as plt

monsters = pd.DataFrame(
    {
        "monster": [
            "Goblin", "Skeleton", "Zombie", "Orc",
            "Hobgoblin", "Ogre", "Owlbear", "Troll",
        ],
        "cr": [0.25, 0.25, 0.25, 0.5, 0.5, 2, 3, 5],
    }
)

counts = monsters.groupby("cr")["monster"].count().sort_index()

fig, ax = plt.subplots(figsize=(7, 4))
ax.bar(counts.index.astype(str), counts.values, color="steelblue")
ax.set(title="Monsters by Challenge Rating", xlabel="Challenge rating",
       ylabel="Number of monsters")
fig.tight_layout()
fig.savefig("cr_by_rating.png", dpi=150)
plt.show()

Install the two libraries if needed, then run the script:

python -m pip install pandas matplotlib
python plot_cr.py

The script creates cr_by_rating.png. In this small example, three monsters have CR 0.25 and two have CR 0.5, so those bars are taller than the others. Before committing, open the image and make sure the labels and counts look sensible. If you adapt this for a CSV, keep the data file in the project or give readers a clear source and download step; otherwise they cannot reproduce the plot. This tiny in-script example keeps the tutorial runnable on its own.

Commit and push the branch

Check what Git sees, then save the script and plot in a commit:

git status
git add plot_cr.py cr_by_rating.png
git commit -m "Add challenge rating plot"
git push -u origin add-cr-plot

git status helps confirm that the files you intend to include are present. git add stages those files for the next commit, and git commit records a snapshot locally with a short description. git push sends the branch to GitHub so you can open a pull request. The -u option connects your local branch to its GitHub copy, so later pushes can use the shorter git push command.

Review the pull request

On GitHub, open the repository and choose Compare & pull request for add-cr-plot. Set the base branch to main and the compare branch to add-cr-plot. Give the pull request a title and a short note explaining the plot. A pull request proposes merging one branch into another; it does not merge the change until you choose to do so.

Read the Files changed tab as if you were reviewing someone else’s work. Does the code count the intended column? Is the plot labeled? Does the generated PNG show the expected result? GitHub can display image changes in a pull request, so including the plot makes the output part of the review. The GitHub pull request documentation walks through creating and reviewing one.

This pause is useful even when you are the only contributor. It separates “I wrote this” from “I checked this,” and leaves a visible history of the decision. If you spot an issue, edit the script on the same branch, run it again, and commit and push the fix. The open pull request updates automatically.

Merge, update, and try it yourself

When the change looks good, click Merge pull request on GitHub and confirm the merge. Then update your local main branch and remove the local feature branch:

git switch main
git pull origin main
git branch -d add-cr-plot

The merge brings the reviewed change into main; pulling downloads that updated branch to your computer. Deleting the local branch is optional cleanup. GitHub may also offer to delete the remote branch after the merge.

For your next small analysis change, try the same sequence: create a branch, make one focused edit, inspect the result, open a pull request, and merge only after your review. You can use this workflow on a solo project or a class lab. The goal is not to add ceremony to every line of code; it is to make meaningful changes easier to check and easier to understand later.
